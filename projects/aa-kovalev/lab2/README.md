# Лабораторная работа №2

## Описание задания

Построить RAG-агента по документации: подготовить не менее 50 страниц, преобразовать
их в Markdown, разбить на чанки, построить эмбеддинги и индекс в Qdrant. Сравнить
три конфигурации по Recall@k, Precision@k и MRR. Ответы LLM должны содержать цитаты
с источником, страницей и фрагментом. Сервис доступен через простую HTML-страницу.

## Использованные технологии и модели

- Python 3.11, uv; версии зависимостей закреплены в `uv.lock`.
- PyMuPDF4LLM — PDF → Markdown; tiktoken `cl100k_base` — измерение размера чанков.
- Qdrant 1.16.3 в Docker; HTTPX — обращения к Qdrant и Ollama.
- Dense-эмбеддинги: `bge-m3:567m` через Ollama `/api/embed`, без обрезания входа.
- Sparse: BM25 (`k1=1.2`, `b=0.75`), разреженные векторы хранятся в Qdrant.
- Hybrid: объединение dense/BM25 через RRF в Qdrant.
- Ответы: `gemma3:4b` из лабы 1 через `/v1/chat/completions`;
  `temperature=0.2`, `max_tokens=512`, три контекстных фрагмента.
- FastAPI, Uvicorn, обычный HTML/JavaScript; интерфейс и API обслуживает один процесс.

### Конфигурации

Все параметры задаются в `config.json`; раздел `variants` переопределяет общие
значения. Можно использовать другой файл через `--config`.

| Вариант | Разбиение | Размер, токены | Overlap | Поиск |
| --- | --- | --- | --- | --- |
| `dense_small` | Markdown-заголовки + окно | 256 | 32 | Dense |
| `dense_large` | Markdown-заголовки + окно | 512 | 64 | Dense |
| `hybrid_large` | Markdown-заголовки + окно | 512 | 64 | Dense + BM25, RRF |

Параметры: `splitter` (`markdown`/`window`), `chunk_size` (100–1000), `overlap`,
`include_headings`, `embedding_model`, `vectorization` (`dense`/`sparse`/`hybrid`).
Размер измеряется `cl100k_base`, включая добавленный заголовок; это не токенизатор
BGE-M3. Хвост раздела может быть короче целевого размера. Чанки не пересекают страницы.
Длинные разделы режутся по окну с сохранением Unicode-символов.

Qdrant: cosine для dense, HNSW `m=16`, `ef_construct=100`, `ef_search=128`;
параметры также в конфигурации. Для малого корпуса снижен порог построения HNSW.
Фактическое состояние коллекции сохраняется в `load.json`. BM25 использует слова
в нижнем регистре, `ё→е`, без стемминга; IDF включён в документный вектор один раз.

Папка индекса и имя коллекции зависят от конфигурации, текста корпуса, digest модели,
кода построения и `uv.lock`. Изменение параметров создаёт новую версию. Повторная
загрузка использует те же ID точек; `--reset` удаляет только выбранную коллекцию.
Артефакты записываются в `artifacts/`, результаты — в `results/`; оба каталога вне git.

### Методика оценки

Эталоны заданы на уровне **страниц**, чтобы сравнение не зависело от разбиения.
Поиск возвращает чанки, затем оставляет наиболее высоко оценённый чанк каждой
страницы. Для небольшого корпуса запрашиваются все точки; это оценка качества
поиска, не тест производительности ANN на большом индексе.

Для каждого вопроса и `k=5,10`:

- Recall@k = найденные релевантные страницы / все размеченные релевантные страницы.
- Precision@k = найденные релевантные страницы / k.
- MRR@k = 1 / позиция первой релевантной страницы; 0, если она не найдена.

Метрики усредняются по 15 вопросам. Вопросы и страницы фиксированы для всех вариантов.
При одной релевантной странице максимальная Precision@5 равна 0.2 — это особенность
такой разметки. Разметка содержит проверенные страницы-основания и может не охватывать
каждое повторение той же информации в книге.

После retrieval формируется 45 ответов: 15 × 3 конфигурации. Сохраняются тексты,
контексты, цитаты, usage, время поиска/генерации, время построения/загрузки и размер
файла индекса. `qa_review.csv` заполняется вручную: правильность ответа и подтверждение
ответа цитатами (`0`/`1`). Наличие синтаксически правильной ссылки само по себе не
доказывает её достоверность. Ноутбук показывает долю проверенных ответов и оценки.

Предварительно для интерфейса выбирается максимум MRR@10, затем Recall@5, затем
минимальное время поиска. Это выбор по retrieval; окончательный вывод учитывает QA
и затраты. Те же 15 вопросов используются для сравнения — независимого теста здесь нет.

## Выводы

Реализован воспроизводимый RAG-пайплайн по одному учебному корпусу. Параметры
разбиения, векторизации и индекса меняются через конфигурацию, ручная очистка не нужна.
HTML-интерфейс выводит ответ и раскрываемые цитаты с переходом на страницу PDF.

Эмпирические выводы о качестве и лучшей конфигурации будут добавлены после запуска
трёх вариантов и проверки ответов. До этого успешную работу с реальными моделями
и значения метрик не утверждаем.

## Инструкция по запуску

Все команды ниже — из `projects/aa-kovalev/lab2`, PowerShell.

1. Запустить Docker Desktop и Ollama. Установить зависимости и модель эмбеддингов:

   ```powershell
   uv sync --locked --group analysis
   ollama pull bge-m3:567m
   ollama pull gemma3:4b
   docker compose up -d
   ```

   Gemma уже установлена в лабе 1; повторный `pull` не обязателен. Эмбеддинги BGE-M3
   требуют отдельной загрузки около 1,2 ГБ. Модели работают последовательно; Ollama
   может выгружать одну при загрузке другой. Qdrant сохраняет данные в Docker volume.

2. Подготовить документы:

   ```powershell
   uv run --locked python source/prepare.py
   ```

   PDF скачается автоматически. Если сайт недоступен, скачать PDF по ссылке выше и
   передать `--pdf C:\путь\AByteofPythonRussian-2.02.pdf`. Контрольная сумма проверяется
   и при ручной загрузке. Markdown лежит в `artifacts/corpus/<hash>/pages/`.

3. Выполнить все три варианта:

   ```powershell
   uv run --locked python source/evaluate.py
   ```

   Команда сама строит и загружает индексы, считает retrieval-метрики и генерирует
   ответы. Для проверки только поиска: `--retrieval-only`. Для принудительной
   пересборки и очистки соответствующих коллекций: `--rebuild --reset`.
   Повторный запуск создаёт новую папку результатов; неизменённые эмбеддинги переиспользуются.

   Отдельные этапы при необходимости:

   ```powershell
   uv run --locked python source/build_index.py --variant dense_small
   uv run --locked python source/load_to_vector_store.py artifacts/indexes/<версия> --reset
   ```

   Вместо `<версия>` подставить путь, который напечатал `build_index.py`.

4. Открыть `source/analysis.ipynb` с интерпретатором `lab2/.venv` и выполнить ячейки.
   Ноутбук выбирает последний успешно завершённый запуск. Проверить ответы и цитаты,
   заполнить два столбца `0`/`1` в `qa_review.csv`, затем пересчитать анализ.

5. Запустить интерфейс:

   ```powershell
   uv run --locked uvicorn app:app --app-dir source --host 127.0.0.1 --port 8000
   ```

   Открыть **http://127.0.0.1:8000**. REST: `POST /ask` с JSON
   `{"question":"Как записать кортеж из одного элемента?"}`. Сервис читает выбранный
   индекс из `artifacts/active.json`; после смены индекса перезапустить сервис.
   Через `load_to_vector_store.py` можно выбрать другую готовую коллекцию.

6. Для анализа передать из новой папки `results/`: `metadata.json`, `runs.jsonl`,
   `summary.csv`, `qa_review.csv`. Реальные метрики и выводы затем войдут в этот README.

Остановка Qdrant без удаления индексов: `docker compose down`.

Источники API: [Ollama embeddings](https://docs.ollama.com/api/embed),
[BGE-M3](https://ollama.com/library/bge-m3),
[Qdrant hybrid search](https://qdrant.tech/documentation/search/hybrid-queries/).
