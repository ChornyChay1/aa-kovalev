# Лабораторная работа №2

## Описание задания

Построить RAG-агента по документации: подготовить не менее 50 страниц, преобразовать
их в Markdown, разбить на чанки, построить эмбеддинги и индекс в Qdrant. Сравнить
конфигурации по Recall@k, Precision@k и MRR. Ответы LLM должны содержать цитаты
с источником, страницей и фрагментом. Сервис доступен через простую HTML-страницу.

## Использованные технологии и модели

- Python 3.11, uv; версии зависимостей закреплены в `uv.lock`.
- PyMuPDF4LLM — PDF → Markdown; `transformers.AutoTokenizer` (`BAAI/bge-m3`) — измерение размера чанков.
- `langchain-text-splitters`: `MarkdownHeaderTextSplitter` и `RecursiveCharacterTextSplitter`.
- Qdrant 1.16.3 в Docker; HTTPX — обращения к Qdrant и Ollama.
- Dense: `bge-m3:567m` через Ollama `/api/embed`, без обрезания входа.
- Sparse: BM25 в Qdrant (`qdrant/bm25`), с русским стеммингом и IDF.
- Ответы: `gemma3:4b` из лабы 1 через `/v1/chat/completions`;
  `temperature=0.2`, `max_tokens=512`, три контекстных фрагмента.
- FastAPI, Uvicorn, обычный HTML/JavaScript; интерфейс и API обслуживает один процесс.

### Конфигурации

Все параметры задаются в `config.json`; раздел `variants` переопределяет общие
значения. Можно использовать другой файл через `--config`.

| Вариант | Разбиение | Размер, токены | Overlap | Поиск |
| --- | --- | --- | --- | --- |
| `dense_small` | Заголовки → Recursive | 384 | 48 | Dense (BGE-M3) |
| `sparse_small` | Заголовки → Recursive | 384 | 48 | Sparse (BM25) |
| `dense_large` | Заголовки → Recursive | 768 | 96 | Dense (BGE-M3) |
| `sparse_large` | Заголовки → Recursive | 768 | 96 | Sparse (BM25) |

Настройки в `config.json`: `chunk_size`, `overlap`, `include_headings`
(`true`/`false`), `embedding_model`, `vectorization` (`dense`/`sparse`).
Варианты образуют сравнение 2×2: Dense/Sparse и 384/768 токенов.
В каждой паре `dense_*`/`sparse_*` параметры разбиения совпадают.
Разделение всегда выполняется двумя этапами:
`MarkdownHeaderTextSplitter` → `RecursiveCharacterTextSplitter`.

`prepare.py` сохраняет единый `book.md` с маркерами страниц и `manifest.json`
с разделами из оглавления PDF. `MarkdownHeaderTextSplitter` сохраняет иерархию
заголовков `#`–`######`, затем маркеры удаляются.
`RecursiveCharacterTextSplitter` формирует чанки, в том числе между страницами;
по положению фрагмента и маркерам определяются `start_page` и `end_page`.
Маркеры не попадают в эмбеддинги. При `include_headings=true` полный путь
заголовков добавляется **в каждый чанк** и учитывается в лимите токенов BGE-M3.
При `false` заголовки остаются только в метаданных.

Размер учитывает специальные токены `BAAI/bge-m3`. Overlap — верхняя
граница перекрытия внутри раздела. Все чанки, начинающиеся на первых двух страницах
корпуса, сохраняются в `artifacts/indexes/<версия>/chunk_example.json`;
путь выводится при построении индекса.

В Dense документы и вопросы кодируются `bge-m3:567m` через Ollama, а Qdrant
хранит готовые векторы. В Sparse Qdrant сам вычисляет BM25-векторы по тексту
с настройкой `language=russian` при загрузке и поиске; Ollama для этого не нужен.
Для каждого Sparse-индекса `avg_len` оценивается средним числом слов в его чанках
(`split()` по примеру из курса Qdrant) и сохраняется в манифесте. Значение
передаётся Qdrant при индексации и поиске вместо стандартных 256.
Это приближение: более точная настройка учитывает токены после удаления стоп-слов.
Начиная с Qdrant 1.20, BM25 по полнотекстовому индексу считает среднюю
длину автоматически, но это иной режим поиска, **без sparse-векторов**.
Для лабораторного сравнения векторов оставлен Qdrant 1.16.3 и BM25-инференс.
Для одинакового разбиения размер чанков в обоих режимах измеряется токенизатором BGE-M3.

Qdrant: cosine для dense, IDF для sparse, HNSW `m=16`, `ef_construct=100`, `ef_search=128`;
параметры также в конфигурации. Для малого корпуса снижен порог построения HNSW.

### Методика оценки

Эталоны в `questions.json` заданы **страницами**, а Qdrant ранжирует и
возвращает **чанки** без разворачивания на отдельные страницы. Чанк считается
релевантным, если его диапазон `start_page`–`end_page` пересекается с
эталонными страницами вопроса. Это приближённая разметка: чанк на нужной
странице не обязательно содержит сам ответ.

Для каждого вопроса и `k=5,10`:

- Recall@k = найденные релевантные чанки / все релевантные чанки индекса.
- Precision@k = найденные релевантные чанки / k.
- MRR@k = 1 / позиция первого релевантного чанка; 0, если он не найден.

Метрики усредняются по 15 вопросам. Страницы эталонов фиксированы для всех
вариантов, а набор релевантных чанков зависит от их разбиения.
В `summary.csv` поле `points_json_bytes` отражает размер промежуточного файла
`points.json`, **не** размер индекса в Qdrant: для Dense это массивы чисел,
для Sparse — тексты с инструкцией серверу построить BM25-векторы.
Сравнивать его как расход памяти индексов нельзя.
На каждом размере чанков Dense и Sparse сравниваются при одинаковом разбиении;
внутри одного метода сравниваются два размера чанка.
Предварительно для интерфейса выбирается максимум MRR@10, затем Recall@5, затем
минимальное время поиска. Это выбор по retrieval; окончательный вывод учитывает QA
и затраты. Те же 15 вопросов используются для сравнения — независимого теста здесь нет.

### Полученные метрики

Числа ниже сохранены из эксперимента с оценкой по уникальным страницам.
Для новой оценки по чанкам нужен отдельный запуск `evaluate.py`;
старые метрики здесь не пересчитывались.

Эксперимент `20261029T222639Z_331af3` (29 октября 2026):
4 конфигурации × 15 одинаковых вопросов = **60 поисковых запросов и 60 ответов Gemma 3**.
В `metadata.json` статус `completed`. Значения ниже получены этим запуском,
а не перенесены из старого эксперимента с другой токенизацией.

| Вариант | Чанки | Recall@5 | Precision@5 | MRR@5 | Recall@10 | Precision@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `dense_small` | 256 | 0.967 | 0.293 | **1.000** | 0.967 | 0.147 | **1.000** |
| `sparse_small` | 256 | 0.900 | 0.267 | 0.839 | 0.967 | 0.147 | 0.848 |
| `dense_large` | 151 | 0.967 | 0.293 | 0.917 | 0.967 | 0.147 | 0.917 |
| `sparse_large` | 151 | 0.933 | 0.280 | 0.863 | 0.967 | 0.147 | 0.863 |

В сохранённом эксперименте `dense_small` первая найденная страница
релевантна для каждого из 15 вопросов (MRR@5 = 1), но этого
недостаточно для гарантии правильного ответа LLM.
При k=10 все варианты достигают одинаковой полноты 0.967.
Низкая Precision@k частично связана с тем, что эталоны содержат мало
релевантных страниц, а знаменатель равен фиксированному k.
На этих данных уменьшение чанков улучшило MRR для Dense,
а Sparse уступил Dense при обоих размерах.

Среднее время получения результата поиска составило 0.078 с (`dense_small`),
0.054 с (`sparse_small`), 0.102 с (`dense_large`) и 0.077 с
(`sparse_large`). Это замеры одного локального запуска, а не стабильный
бенчмарк производительности. BM25 `avg_len` для Sparse был вычислен по
каждому набору чанков: 98.74 (`small`) и 157.87 (`large`) слова в среднем.

### Ручная QA-проверка

Все **60 ответов** проверены по эталонным ответам, вопросу и фактически
цитируемым фрагментам из `runs.jsonl`. Два независимых бинарных критерия:

- **Верность** (1/0): ответ фактически правильный, отвечает на обе части
  вопроса, если их две, и не содержит существенных ошибочных утверждений.
- **Подтверждение цитатами** (1/0): среди указанных ссылок имеется
  фрагмент, непосредственно подтверждающий ключевые утверждения ответа.
  Лишние нерелевантные ссылки помечались отдельно в замечаниях;
  они не обнуляли оценку, если нужный источник тоже присутствовал.

| Вариант | Правильные ответы | Подтверждены цитатами |
| --- | ---: | ---: |
| `dense_small` | **13/15 (86.7%)** | 13/15 |
| `sparse_small` | 11/15 (73.3%) | 12/15 |
| `dense_large` | 12/15 (80.0%) | **14/15** |
| `sparse_large` | 10/15 (66.7%) | 11/15 |

Ошибки, выявленные при ручной проверке:

- **Q02, `dense_small`** — неправильно объяснено, что `2things` запрещено
  из-за пробелов. В извлечённом фрагменте на PDF-стр. 47 также находится
  неоднозначная/ошибочная фраза про пробелы; причина в Python — цифра
  в начале идентификатора. `dense_large` вообще уходит в ссылки на списки.
  `sparse_large` ошибочно допускает цифру первым символом.
- **Q06, `dense_small`** — объяснение `global` упускает главное:
  присваивание имени модуля внутри функции, вместо создания локального.
- **Q03, `sparse_small`** — ответ «отступы определяют блоки» не
  раскрывает правила одинакового отступа и ошибки при нарушении.
- **Q10, оба Sparse-варианта** — модель отказывается отвечать на
  вопрос о `__name__`, хотя ответ есть в учебнике (PDF-стр. 85–86).
- **Q11–Q12, `sparse_small`** — не объяснён синтаксис кортежа и
  дан неверный пример `(2)` вместо `(2,)`.
- **Q04 и Q08, `sparse_large`** — противоречивое объяснение
  `while ... else` после `break` и неверное ограничение, будто
  ключевые аргументы допустимы лишь для параметров с default.
- **Q07, оба `large`** — повторено утверждение учебника, что
  значение аргумента по умолчанию обязательно должно быть константой.
  В Python изменяемые значения технически разрешены, хотя их применение
  часто опасно. Это пример фактически неверного, но подтверждённого
  источником утверждения.
- **Q09, `dense_large`** — описан `return` без значения, но явно
  не дан ответ о функции совсем без `return`: она возвращает `None`.

Некоторые правильные ответы также содержат неверно выбранные **номера цитат**:
например, `dense_small` в Q01 указывает [3] с общим описанием типов
данных, а не с перечнем трёх типов чисел. В этом запуске один и тот же чанк иногда
попадал в контекст под разными номерами, поскольку поиск сначала
выбирал **уникальные страницы**, а не уникальные чанки.
Теперь `retrieve()` возвращает непосредственно чанки, а `answer()`
передаёт первые три без дублирования. Повторная оценка не проводилась.

**Итог:** для интерфейса оставлен `dense_small`: он первый по MRR@10
и по ручной доле правильных ответов в этом запуске. Преимущество показано
только на 15 заранее размеченных вопросах, поэтому не следует считать его
доказательством превосходства на независимых данных. Ручная QA-оценка
не автоматизирована; её выставленные оценки не используются при поиске
и выборе конфигурации.

## Инструкция по запуску

Все команды ниже — из `projects/aa-kovalev/lab2`, PowerShell.

1. Запустить Docker Desktop и Ollama. Установить зависимости и модель эмбеддингов:

   ```powershell
   uv sync --locked
   ollama pull bge-m3:567m
   ollama pull gemma3:4b
   docker compose up -d
   ```

2. Подготовить документы:

   ```powershell
   uv run --locked python source/prepare.py
   ```

   PDF скачается автоматически. Если сайт недоступен, скачать PDF по ссылке выше и
   передать `--pdf C:\путь\AByteofPythonRussian-2.02.pdf`. Контрольная сумма проверяется
   и при ручной загрузке. Корпус хранится в `artifacts/corpus/<hash>/`:
   `book.pdf`, `book.md`, `manifest.json`. Старые `pages.json` и папка `pages/`
   удаляются при обновлении корпуса.

3. Выполнить сравнение:

   ```powershell
   uv run --locked python source/evaluate.py
   ```

   Команда сама строит и загружает индексы, считает retrieval-метрики и генерирует
   ответы. Для проверки только поиска: `--retrieval-only`. Для принудительной
   пересборки и очистки соответствующих коллекций: `--rebuild --reset`.
   Полный запуск выполняет 4 варианта × 15 вопросов, включая генерацию ответов LLM.
   Повторный запуск создаёт новую папку результатов; неизменённые эмбеддинги переиспользуются.

4. Запустить интерфейс:

   ```powershell
   uv run --locked uvicorn app:app --app-dir source --host 127.0.0.1 --port 8000
   ```

   Открыть **http://127.0.0.1:8000**. REST: `POST /ask` с JSON
   `{"question":"Как записать кортеж из одного элемента?"}`. Сервис читает выбранный
   индекс из `artifacts/active.json`; после смены индекса перезапустить сервис.
   Через `load_to_vector_store.py` можно выбрать другую готовую коллекцию.

5. Для ревью отправить ZIP с **четырьмя файлами** из последней папки `results/<запуск>/`:
   `summary.csv` (сводные метрики), `runs.jsonl` (поиск и ответы по вопросам),
   `metadata.json` (настройки и статус), `qa_review.csv` (ответы LLM для ручной проверки).
   Файлы из `artifacts/indexes/`, PDF и эмбеддинги отправлять не нужно.
   Результаты эксперимента и независимой ручной QA-проверки описаны выше;
   при повторном запуске оценки QA необходимо проверять заново.

Остановка Qdrant без удаления индексов: `docker compose down`.

Источники API: [Ollama embeddings](https://docs.ollama.com/api/embed),
[BGE-M3](https://ollama.com/library/bge-m3).
