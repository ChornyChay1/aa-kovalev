# Лабораторная работа №1

## Описание задания

Развернуть три LLM разных семейств через OpenAI-совместимый REST API,
сравнить ответы на три русских промпта в базовом режиме и после изменения
гиперпараметров. Сохранить ответы и измерения, оценить качество и устойчивость.

## Использованные технологии и модели

- Движок: локальный Ollama.
- API: `http://localhost:11434/v1/chat/completions`.
- Python 3.11, менеджер зависимостей uv, HTTP-клиент httpx, psutil для поиска локального процесса модели.
- Целевое оборудование: NVIDIA RTX 3060 Laptop, 6 ГБ видеопамяти.

| Модель в Ollama | Семейство | Квантование | Размер загрузки |
| --- | --- | --- | --- |
| `qwen2.5:3b` | Qwen | Q4_K_M | около 1,9 ГБ |
| `llama3.2:3b` | Llama | Q4_K_M | около 2,0 ГБ |
| `gemma3:4b` | Gemma | Q4_K_M | около 3,3 ГБ |

Размер загрузки не равен расходу видеопамяти: дополнительно нужны память для
контекста и рабочие буферы. Модели запускаются по очереди с контекстом 4096
токенов. Ожидается, что такой режим подойдёт для видеокарты; фактическое
размещение и скорость нужно проверить на ноутбуке. Желательно от 16 ГБ ОЗУ.
Русский не входит в официально поддерживаемые языки Llama 3.2, поэтому качество
на русских заданиях оценивается отдельно. Для Gemma используются только тексты.

Теги могут обновляться. Перед экспериментом нужно сохранить версию Ollama,
идентификаторы моделей, параметры из `ollama show --modelfile` и данные оборудования.

Источники:
- [Qwen 2.5 3B](https://ollama.com/library/qwen2.5:3b)
- [Llama 3.2 3B](https://ollama.com/library/llama3.2:3b)
- [Gemma 3 4B](https://ollama.com/library/gemma3:4b)
- [OpenAI-совместимый API Ollama](https://docs.ollama.com/api/openai-compatibility)
- [Характеристики RTX 30 Laptop](https://www.nvidia.com/en-us/geforce/laptops/30-series/)

## Результаты работы

Подготовлены скрипт проверки API и `source/run_experiment.py`. Исходные промпты,
эталоны для классификации и извлечения, критерии письма находятся в `prompts.json`.
Эксперимент выполнен 4 октября 2026 на RTX 3060 Laptop: 90 основных ответов и
90 дополнительных генераций, все завершились без ошибок. Данные сохранены в
`data/run_20261004/`, воспроизводимый анализ — в `source/analysis.ipynb`.
Ответ проверочного запроса не входит в результаты лабораторной.

План эксперимента:
- P1: письмо о переносе встречи с заданными фактами и ограничением длины.
- P2: классификация обращений по фиксированным меткам с эталонными ответами.
- P3: извлечение полей товара в JSON; отсутствующие значения — `null`.
- A: параметры генерации не передаются, используются настройки Ollama и модели.
- B: `temperature=0.2`, `top_p=0.8`, `max_tokens=512`.
  Параметры модели сохраняются из `/api/show`; нужно проверить их при анализе.
- По пять повторов каждой комбинации: 3 модели × 3 промпта × 2 режима × 5 = 90 ответов.
- Прогрев отделяется от измерений; в каждом запросе новая история сообщений.
- Сохраняются полные запросы и ответы, режим, номер повтора, время запроса,
  число входных и выходных токенов, причина завершения и доступные метрики движка.
- Порядок A/B чередуется между повторами; seed не фиксируется, принудительный
  JSON mode не включается. Формат ответа задаётся только текстом промпта.

Контекст и ограничения загрузки одинаковы для A и B. Скорость обработки промпта
нельзя называть скоростью токенизации, а токены ответа, делённые на полное время
запроса, — чистой скоростью генерации. Отдельные серверные длительности и скорость
токенизации через этот endpoint недоступны. Они измеряются дополнительно:
- Для каждого основного прогона выполняется отдельный запрос `/api/chat` с теми же
  сообщениями и настройками. Его ответ, запрос и длительности сохраняются в
  `native_measurement`. Это собственная генерация, её время не приписывается
  основному ответу из `/v1/chat/completions`.
- Скорость серверной генерации: `eval_count / (eval_duration / 1e9)`.
- Сохраняются длительности загрузки модели, обработки промпта и всей серверной операции.
  Скорость обработки некэшированных входных токенов вычисляется только при наличии
  счётчика кэшированных токенов. При полностью кэшированном входе измерение не
  характеризует производительность обработки нового промпта.
- Для каждого промпта каждой модели отдельно вызывается внутренний `/tokenize`
  локального runner: один прогрев и 20 замеров, медиана времени и токенов в секунду.
  Измеряется сырой текст без шаблона диалога и специальных токенов. Число токенов
  поэтому может отличаться от `prompt_tokens` основного запроса.
- Время токенизации включает локальный HTTP-вызов и разбор ответа. Это скорость
  сервиса токенизации, а не изолированное время вычислений токенизатора. У коротких
  промптов служебные задержки могут составлять заметную часть результата.

Для токенизации используется токенизатор фактически загруженной модели, скачивать
его отдельно не нужно. Внутренний endpoint не является стабильным публичным API:
скрипт ищет локальный процесс Ollama/llama с нужным файлом модели и портом. Если
версия Ollama не поддерживает этот способ или доступ к процессу запрещён, ошибка
явно сохраняется в `metadata.json`, эксперимент получает `completed_with_errors`.
При удалённом сервере этот способ недоступен. Ошибки нужно проверить перед отчётом.

Кэш Ollama не очищается, доступный счётчик `cached_tokens` сохраняется.
Дополнительная генерация всегда идёт после основной, поэтому её вход может уже
находиться в кэше. Это учитывается при анализе времени обработки промпта.

Каждый запуск создаёт отдельную папку `results/<время>_<идентификатор>/`:

| Файл | Содержимое |
| --- | --- |
| `runs.jsonl` | Один основной прогон на строку: запрос, ответ, параметры, usage, метрики, исходные JSON-фрагменты потока, дополнительная генерация с серверными метриками, размещение модели, ошибки |
| `metadata.json` | Снимок промптов и эталонов, версии, идентификаторы и параметры моделей, данные GPU, прогревы, отдельные замеры токенизации, статус эксперимента |
| `summary.csv` | Средние значения и стандартные отклонения по модели/промпту/режиму, повторяемость ответов, скорость серверной генерации, время и скорость вызова токенизатора |

Измеряемые показатели:
- `elapsed_s`: полное время генерационного HTTP-запроса, без последующего сбора диагностики.
- `first_text_s`: время до первого непустого текстового фрагмента на клиенте.
- `response_headers_s`, `last_text_s`: время получения заголовков и последнего текстового фрагмента.
- `prompt_tokens`, `completion_tokens`, `total_tokens`, `cached_prompt_tokens`: данные сервера; отсутствующие значения — `null`.
- `output_tokens_per_request_second`: выходные токены / полное время запроса.
- `answer_chars`, `answer_words`: символы и слова; это не замена токенам LLM.
- `repeated_word_trigram_fraction`: доля повторных троек слов после первого вхождения.
- `native_measurement.metrics.server_generation_tokens_per_s`: серверная скорость
  дополнительной генерации, измеренная для её собственного ответа.
- `tokenization_benchmarks` в метаданных: 20 длительностей вызова токенизатора,
  число токенов сырого промпта, медиана времени и скорость. В сводке эти значения
  повторяются для A/B: это один независимый замер для модели/промпта, а не пять
  отдельных замеров токенизации в каждом режиме.

Поля серверного времени и токенизации в основном `metrics` остаются `null`:
смотрите вложенный `native_measurement` и отдельный `tokenization_benchmarks`.

Число уникальных ответов и частота самого распространённого ответа характеризуют
наблюдаемую устойчивость текста на пяти повторах, но не доказывают детерминизм.
Фактические ошибки и качество оцениваются по сохранённым ответам и эталонам позже.
При ошибке прогон сохраняется без автоматического повтора, скрипт продолжает работу.
При Ctrl+C ранее завершённые прогоны остаются в файле. Если основной ответ уже
получен, а дополнительная генерация прервана, он сохраняется с
`native_measurement.status=pending`. Незавершённый основной ответ не сохраняется.
Повторный запуск создаёт новую папку, результаты не перезаписываются. Папка `results/`
исключена из git; для анализа файлы нужно передать отдельно.

## Инструкция по запуску

### 1. Установить Ollama и uv

Установить [Ollama](https://ollama.com/download/windows) и
[uv](https://docs.astral.sh/uv/getting-started/installation/).
Python 3.11 при необходимости будет установлен uv при синхронизации.

### 2. Настроить Ollama для ноутбука

В PowerShell задать настройки сервера:

```powershell
[Environment]::SetEnvironmentVariable("OLLAMA_CONTEXT_LENGTH", "4096", "User")
[Environment]::SetEnvironmentVariable("OLLAMA_MAX_LOADED_MODELS", "1", "User")
[Environment]::SetEnvironmentVariable("OLLAMA_NUM_PARALLEL", "1", "User")
```

Полностью закрыть Ollama через значок в области уведомлений и открыть заново.
Если переменные ещё не подхватились, выйти из учётной записи Windows и войти снова.
Для ручного запуска вместо приложения можно использовать отдельный PowerShell:

```powershell
$env:OLLAMA_CONTEXT_LENGTH = "4096"
$env:OLLAMA_MAX_LOADED_MODELS = "1"
$env:OLLAMA_NUM_PARALLEL = "1"
ollama serve
```

Запускать один сервер: приложение Ollama либо `ollama serve`.

### 3. Скачать модели

```powershell
ollama pull qwen2.5:3b
ollama pull llama3.2:3b
ollama pull gemma3:4b
ollama list
```

Суммарная загрузка — около 7,2 ГБ. Все три модели хранить на диске можно,
в видеопамять загружается одна модель за раз.

### 4. Подготовить Python-окружение

Из корня репозитория:

```powershell
cd projects/aa-kovalev/lab1
uv sync --locked
```

### 5. Проверить API

```powershell
uv run --locked python source/check_connection.py --model qwen2.5:3b
uv run --locked python source/check_connection.py --model llama3.2:3b
uv run --locked python source/check_connection.py --model gemma3:4b
```

Скрипт обращается к `/v1/models` и `/v1/chat/completions`. Параметры генерации
не передаются. Адрес можно изменить через `--base-url`.
Первый запрос может занимать больше времени из-за загрузки модели.

После запроса проверить размещение модели:

```powershell
ollama ps
nvidia-smi
ollama --version
ollama show --modelfile qwen2.5:3b
ollama show --modelfile llama3.2:3b
ollama show --modelfile gemma3:4b
```

В `ollama ps` проверить столбцы `PROCESSOR` и `CONTEXT`. Если часть модели
работает на CPU, закрыть приложения, занимающие видеопамять, и повторить проверку.
Если потребуется уменьшить контекст, сделать это одинаково для всех запусков
и записать новое значение в отчёт.

### 6. Выполнить эксперимент

Из каталога `projects/aa-kovalev/lab1`:

```powershell
uv run --locked python source/run_experiment.py
```

По умолчанию выполняются 90 основных прогонов, 90 дополнительных генераций
для серверных измерений, три отдельных прогрева и замеры токенизации.
Скрипт выводит путь к результатам и прогресс. Запросы последовательные, каждая
модель проходит все свои задания перед загрузкой следующей.
Перед запуском закрыть приложения, активно использующие GPU, подключить ноутбук
к питанию и не запускать другие запросы к Ollama во время эксперимента.

Для короткой проверки всей цепочки (18 прогонов):

```powershell
uv run --locked python source/run_experiment.py --repeats 1
```

Для отдельной модели или большего времени ожидания:

```powershell
uv run --locked python source/run_experiment.py --models qwen2.5:3b --timeout 600
```

`--timeout` задаёт таймаут сетевых операций, включая ожидание очередного фрагмента,
а не жёсткий лимит полного времени генерации. Если базовый ответ затянулся, можно
остановить запуск через Ctrl+C. Параметр `max_tokens` в A намеренно не задаётся.
Для совместного анализа передать `runs.jsonl`, `metadata.json` и `summary.csv`
из одной папки завершённого эксперимента. Итоговый отчёт будет заполнен после анализа.

### 7. Открыть анализ сохранённого запуска

```powershell
uv sync --locked --group analysis
```

Открыть `source/analysis.ipynb` в VS Code с расширением Jupyter. Выбрать Python
из `lab1/.venv` и выполнить все ячейки. Ноутбук содержит сохранённые результаты
выполнения и не отправляет запросы к моделям. Запускать его можно из `lab1` или
`lab1/source`; исходные данные лежат рядом в `data/run_20261004`.

JSONL сжат без изменения содержания. Исходный `summary.csv` сохранён для сверки;
ноутбук пересчитывает таблицы из ответов. В этом запуске Ollama вернул серверные
`timings` через OpenAI-совместимый API, поэтому скорость основных ответов вычисляется
из них, без подстановки метрик дополнительного ответа. Время токенизации включает
локальный HTTP-вызов. Кэш и первый медленный запрос Gemma разобраны отдельно.
