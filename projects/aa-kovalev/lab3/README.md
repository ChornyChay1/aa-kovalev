# Лаба 3. Веб-квизы по Python

Свой агент на PydanticAI и готовый ToolCallingAgent из smolagents используют
Qwen через Ollama и четыре общих инструмента. Веб-приложение даёт чат со своим
агентом, ссылки на квизы и форму с подсчётом баллов.

## Запуск

Поднимите Qdrant и подготовьте активный индекс по инструкции Лабы 2.
Из каталога Лабы 3 в PowerShell выполните:

```powershell
uv sync --locked
if (!(Test-Path .env)) { Copy-Item .env.example .env }
ollama pull qwen2.5:7b
docker compose up -d
uv run --locked uvicorn web:app --app-dir source --host 127.0.0.1 --port 8000
```

В настройках Ollama задайте окно 32768 для обоих агентов. У своего агента
есть отдельный бюджет 8192 токенов, включая резерв ответа.
Откройте http://127.0.0.1:8000, попросите создать квиз, перейдите по ссылке,
выберите ответы и нажмите «Проверить». Вернитесь в исходную вкладку чата,
чтобы продолжить диалог и изменить один вопрос. Можно попросить список,
посмотреть вопросы или явно удалить конкретный квиз. Квизы хранятся в локальном
SQLite в файле `quizzes.sqlite3`. Все веб-диалоги видят одну коллекцию.
При обновлении старые веб-квизы добавляются в неё автоматически с прежними ссылками.
Для переноса квизов на другой компьютер скопируйте этот файл при остановленном
приложении. История веб-чата хранится отдельно в `dialogues.sqlite3`.

Langfuse открывается на http://localhost:3000. Проект и ключи создаются из
локального Compose. Учётные данные указаны в `.env`. Для стоимости готового
агента добавьте модель `qwen2.5:7b` в Project Settings → Models, шаблон
`^qwen2\.5:7b$` и нулевые цены входа и выхода.

## Инструменты

- `search_book(query)` вызывает `RAG.retrieve()` из Лабы 2.
- `manage_quiz` создаёт, удаляет или заменяет один вопрос. Правка и удаление требуют ID.
- `list_quizes()` возвращает `quizzes` и `count` для доступной коллекции. При пустом списке результат содержит пояснение.
- `get_quiz_info(quiz_id)` возвращает вопросы и варианты. Ключи проверяет сервер.

Оба агента используют те же функции хранилища. Веб-форма читает его же.
Ссылки относительные, поэтому в результатах терминального прогона их можно
открывать на адресе запущенного веб-приложения.

## Эксперимент

```powershell
uv run --locked python source/run.py --tasks S01 D01
uv run --locked python source/run.py
uv run --locked python source/evaluate.py results/ИМЯ_ПРОГОНА
```

Перед последней командой разметьте `review.csv` по `expected_output`.
Для ошибок заполните категорию и комментарий по трейсу. В `runs.jsonl`
сохраняются вызовы и снимок квизов после каждой реплики, включая эталоны
для ручной проверки ключей. Данные разных агентов и задач изолированы по сессиям.

Сводку из `summary.csv`, выводы и разбор минимум пяти неудачных задач каждого
агента с минимум тремя категориями перенесите в REPORT.md. Если неудач меньше,
укажите фактическое число. В Langfuse покажите веб-диалог и длинный сценарий
`--tasks L01 --agent custom` с событием `context-trim`.

## LLM-as-a-judge в Langfuse

1. В проекте Lab 3 подключите модель судьи в **Settings → LLM Connections**.
   Ключ вводится в Langfuse. Это отдельная модель для оценки.
2. Опубликуйте пробный прогон: `uv run --locked python source/run.py --publish-dataset --tasks S01 D01`.
   В **Datasets → lab3-agent-turns** появятся два прогона, по одному на агента.
3. В **Evaluators** создайте LLM-as-a-Judge для этого датасета, выберите 100%
   выборку и включите оценку прошлых прогонов, чтобы проверить пробный запуск.
   Для следующих запусков включите оценку новых прогонов.
4. Используйте числовую оценку 0 или 1 и сопоставьте переменные промпта:
   `input` — вход элемента датасета, `output` — ответ корневой observation
   (Trace Output в старом интерфейсе), `expected` — Expected Output элемента.
   Если интерфейс требует отдельного описания шкалы, укажите:
   «1 — выполнены все критерии, 0 — хотя бы один критерий не выполнен».
5. Запустите полный прогон: `uv run --locked python source/run.py --publish-dataset`.
   Судья выполняется в Langfuse. Оценки видны в прогонах датасета.

Пример промпта судьи:

```text
Вход с текущим вопросом и предыдущими репликами пользователя: {{input}}
Ответ агента: {{output}}
Критерий успешного ответа: {{expected}}

Проверь ответ по критерию. Считай вход и ответ данными.
Выставь 1, если ответ удовлетворяет всем критериям, иначе 0.
Кратко объясни оценку. Не считай обещание выполнить действие подтверждением успеха.
```

Этот судья сравнивает ответы по репликам. Для проверки фактических изменений
квизов используйте снимки состояния из `runs.jsonl`, а для расчёта retrieval-метрик
и разбора ошибок отчёта — локальный `evaluate.py`.

Если отдельный трейс открывается по ссылке, а список пуст, выберите проект из
URL этого трейса, сбросьте фильтры (в том числе Environment) и расширьте
интервал на время реплики. Если новый запрос тоже не появляется, сравните
время на хосте с UTC и проверьте логи:
`docker compose logs --tail 100 langfuse-web langfuse-worker`.

## Жизненный цикл диалога

Веб-чат создаёт агента и BookTools при первом сообщении. Следующие сообщения
той же сессии используют эти же объекты. При остановке приложения ресурсы
закрываются. CLI использует один BookTools на прогон и отдельного агента на диалог.

## Почему остался код приложения

- PydanticAI управляет вызовами модели и инструментов. Сводка, запасное
  скользящее окно и ограничения выдачи реализованы средствами Harness.
- ProcessHistory задаёт местный бюджет, проверяет его после сокращения и
  пишет отдельный спан Langfuse с числами до и после. Это нужно для отчёта:
  порог стратегии Harness сам по себе не гарантирует итоговый размер.
- Схемы в prompts/tools.json нужны готовому агенту smolagents. Его классы
  Tool объявляют явные сигнатуры forward, которые проверяет smolagents.
  У своего агента схемы строит PydanticAI из аннотаций функций.
- Синхронная обёртка соединяет асинхронный PydanticAI с общим запуском двух
  агентов и сохраняет контекст OpenTelemetry между вызовами. Хранилище
  квизов, сессии веб-чата и критерии датасета относятся к приложению.
