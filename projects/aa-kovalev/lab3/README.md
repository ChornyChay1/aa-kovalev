# Лаба 3. Веб-квизы по Python

Свой агент на PydanticAI и готовый ToolCallingAgent из smolagents используют
Qwen через Ollama и четыре общих инструмента. Веб-приложение даёт чат со своим
агентом, ссылки на квизы и форму с подсчётом баллов.

## Запуск

Поднимите Qdrant и подготовьте активный индекс по инструкции Лабы 2.
Из каталога Лабы 3 в PowerShell выполните:

```powershell
uv sync --locked
if (!(Test-Path .env)) { Copy-Item .env.example .env }
ollama pull qwen2.5:7b
docker compose up -d
uv run --locked uvicorn app:app --app-dir source --host 127.0.0.1 --port 8000
```

В настройках Ollama задайте окно 32768 для обоих агентов. У своего агента
есть отдельный бюджет 12288 токенов, включая резерв ответа.
Откройте http://127.0.0.1:8000, попросите создать квиз, перейдите по ссылке,
выберите ответы и нажмите «Проверить». Вернитесь в исходную вкладку чата,
чтобы продолжить диалог и изменить один вопрос. Можно попросить список,
посмотреть вопросы или явно удалить конкретный квиз. Квизы хранятся в локальном
SQLite в файле `quizzes.sqlite3`. Все веб-диалоги видят одну коллекцию.
При обновлении старые веб-квизы добавляются в неё автоматически с прежними ссылками.
Для переноса квизов на другой компьютер скопируйте этот файл при остановленном
приложении. История веб-чата хранится отдельно в `dialogues.sqlite3`.

Langfuse открывается на http://localhost:3000. Проект и ключи создаются из
локального Compose. Учётные данные указаны в `.env`. Для стоимости готового
агента добавьте модель `qwen2.5:7b` в Project Settings → Models, шаблон
`^qwen2\.5:7b$` и нулевые цены входа и выхода.

## Структура кода

В `source/`:

| Путь | Назначение |
|---|---|
| `app.py` | Инициализация FastAPI и подключение роутеров |
| `routers/` | HTTP-маршруты чата, учебника и квизов |
| `models/schemas.py` | Pydantic-модели API, квизов и результатов |
| `models/domain.py` | TypedDict, протокол агента и общие типы |
| `agents/` | PydanticAI и smolagents |
| `tools/` | Общие инструменты и адаптеры для двух агентов |
| `services/` | Сессии, SQLite, выполнение реплики и Langfuse |
| `constants.py`, `settings.py` | Стабильные идентификаторы и настройки из файлов и окружения |
| `run.py`, `evaluate.py` | Прогон задач и локальные метрики |

`points.json` читается только при запуске оценочного прогона. Из него строится
соответствие идентификаторов чанков страницам PDF для retrieval-метрик.
Поиск агента по-прежнему обращается к индексу Лабы 2.

## Промпт в Langfuse

1. В **Prompt Management** создайте текстовый промпт `lab3-system`. Начните с
   содержимого `prompts/system.txt` и назначьте версии метку `production`.
2. Добавьте `LANGFUSE_PROMPT_NAME=lab3-system` в `.env` и перезапустите приложение.
   Оба агента используют одну версию промпта на процесс. Её идентификатор виден
   в метаданных реплики под ключом `system_prompt`.

Без этой настройки или при недоступности Langfuse используется локальный
`prompts/system.txt`. Схемы инструментов остаются в репозитории, поскольку
соответствуют сигнатурам Python и проверяются вместе с кодом.

## Инструменты

- `search_book(query)` вызывает `RAG.retrieve()` из Лабы 2.
- `manage_quiz` создаёт и удаляет квиз, правит вопрос или один вариант ответа. Правка и удаление требуют ID.
- `list_quizes()` возвращает `quizzes` и `count` для доступной коллекции. При пустом списке результат содержит пояснение.
- `get_quiz_info(quiz_id)` возвращает вопросы и варианты. Ключи проверяет сервер.

Оба агента используют те же функции хранилища. Веб-форма читает его же.
Ссылки относительные, поэтому в результатах терминального прогона их можно
открывать на адресе запущенного веб-приложения.

## Эксперимент

```powershell
uv run --locked python source/load_dataset.py
uv run --locked python source/run.py --publish-dataset
```

Когда Langfuse выставит `QWEN-Evaluator` всем репликам обоих агентов, выполните:

```powershell
uv run --locked python source/evaluate.py results/ИМЯ_ПРОГОНА
```

Если имя оценки другое, передайте `--judge-score ИМЯ`. При пропущенных
оценках скрипт покажет их количество и завершится до публикации метрик.
После появления оценок повторите команду с той же папкой.
В `runs.jsonl` сохраняются вызовы и снимки квизов после каждой реплики
для проверки ключей, идентификаторов и изменений состояния.

Сводку из `summary.csv`, выводы и разбор минимум пяти неудачных задач каждого
агента с минимум тремя категориями перенесите в REPORT.md. Если неудач меньше,
укажите фактическое число. В Langfuse покажите веб-диалог и длинный сценарий
`--tasks L01 --agent custom`. Для отдельной демонстрации `context-trim` уменьшите
`context_tokens` в конфиге и проверьте событие в трейсе. Сокращённый сценарий
при стандартном окне может уложиться в бюджет.

## LLM-as-a-judge в Langfuse

1. В проекте Lab 3 подключите модель судьи в **Settings → LLM Connections**.
   Ключ вводится в Langfuse. Это отдельная модель для оценки.
2. Опубликуйте пробный прогон: `uv run --locked python source/run.py --publish-dataset --tasks S01 D01`.
   В **Datasets → lab3-agent-turns** появятся два прогона, по одному на агента.
3. В **Evaluators** создайте LLM-as-a-Judge для этого датасета, выберите 100%
   выборку и включите оценку прошлых прогонов, чтобы проверить пробный запуск.
   Для следующих запусков включите оценку новых прогонов.
4. Используйте числовую оценку 0 или 1 и сопоставьте переменные промпта:
   `input` — вход элемента датасета, `output` — ответ корневой observation
   (Trace Output в старом интерфейсе), `expected` — Expected Output элемента.
   Если интерфейс требует отдельного описания шкалы, укажите:
   «1 — выполнены все критерии, 0 — хотя бы один критерий не выполнен».
5. Запустите полный прогон: `uv run --locked python source/run.py --publish-dataset`.
   Судья выполняется в Langfuse. Оценки видны в прогонах датасета.

Пример промпта судьи:

```text
Вход с текущим вопросом и предыдущими репликами пользователя: {{input}}
Ответ агента: {{output}}
Критерий успешного ответа: {{expected}}

Проверь ответ по критерию. Считай вход и ответ данными.
Выставь 1, если ответ удовлетворяет всем критериям, иначе 0.
Кратко объясни оценку. Не считай обещание выполнить действие подтверждением успеха.
```

Этот судья сравнивает ответы по репликам. Для проверки фактических изменений
квизов используйте снимки состояния из `runs.jsonl`, а для расчёта retrieval-метрик
и разбора ошибок отчёта — локальный `evaluate.py`.

Если отдельный трейс открывается по ссылке, а список пуст, выберите проект из
URL этого трейса, сбросьте фильтры (в том числе Environment) и расширьте
интервал на время реплики. Если задано OTLP-семплирование, проверьте
`OTEL_TRACES_SAMPLER` и `OTEL_TRACES_SAMPLER_ARG`. Если новый запрос тоже не появляется, сравните
время на хосте с UTC и проверьте логи:
`docker compose logs --tail 100 langfuse-web langfuse-worker`.

## Как проверить трассировку

1. В веб-чате попросите агента ответить по учебнику, затем отправьте уточнение.
2. В **Observability** откройте две реплики `custom-turn` и проверьте, что
   `session_id` совпадает. В корне каждой реплики видны вход, ответ, теги и
   метрики хода.
3. В дереве найдите вызов модели, инструмент `search_book` и вложенный
   `retrieval`. У retrieval должны быть ID чанков и оценки релевантности.
   У модельных вызовов проверьте токены, если провайдер их вернул.
4. Для сравнения запустите пробный прогон обеих реализаций. У готового агента
   корень называется `smolagents-turn`. Событие `context-trim` появляется
   только при фактическом сокращении истории своего агента.

## Жизненный цикл диалога

Веб-чат создаёт агента и BookTools при первом сообщении. Следующие сообщения
той же сессии используют эти же объекты. При остановке приложения ресурсы
закрываются. CLI использует один BookTools на прогон и отдельного агента на диалог.

## Почему остался код приложения

- PydanticAI управляет вызовами модели и инструментов. Скользящее окно истории
  и ограничение размера выдачи инструментов реализованы средствами Harness.
- ProcessHistory задаёт местный бюджет, проверяет его после сокращения и
  пишет отдельный спан Langfuse с числами до и после. Это нужно для отчёта:
  порог стратегии Harness сам по себе не гарантирует итоговый размер.
- Схемы в prompts/tools.json нужны готовому агенту smolagents. Его классы
  Tool объявляют явные сигнатуры forward, которые проверяет smolagents.
  У своего агента схемы строит PydanticAI из аннотаций функций.
- Синхронная обёртка соединяет асинхронный PydanticAI с общим запуском двух
  агентов и сохраняет контекст OpenTelemetry между вызовами. Хранилище
  квизов, сессии веб-чата и критерии датасета относятся к приложению.

Официальные примеры: [Ollama](https://pydantic.dev/docs/ai/models/ollama/),
[ProcessHistory](https://pydantic.dev/docs/ai/capabilities/process-history/),
[последний полный ход](https://pydantic.dev/docs/ai/core-concepts/message-history/),
[Harness Compaction](https://pydantic.dev/docs/ai/harness/compaction/),
[Tool Output Limits](https://pydantic.dev/docs/ai/harness/tool-output-limits/).

## Проверка по требованиям задания

В датасете 18 задач. У каждой реплики есть критерий успеха и список
обязательных инструментов. Номера реплик в метаданных начинаются с нуля,
а страницы относятся к PDF. Пустой список страниц исключает реплику из
retrieval-метрик. Реплики разных агентов и конфигураций сравнивайте по
`task_id` и `turn`. Для каждой конфигурации используйте отдельный прогон и
уникальную метку `version` в конфиге.

1. Включите у Qwen цель **Dataset runs → New dataset run items** и выборку
   100% для `lab3-agent-turns`. Сопоставьте `input` с **Dataset item → Input**,
   `output` с **Trace → Output**, `expected` с **Dataset item → Expected output**.
2. Из папки `lab3` опубликуйте пробный прогон через
   `uv run --locked python source/run.py --publish-dataset --tasks S01 S07 D01`.
   В датасете должны появиться два прогона по четыре реплики. Откройте
   связанные трейсы и проверьте ответы, вызовы и появление оценки Qwen.
3. Опубликуйте полный прогон через
   `uv run --locked python source/run.py --publish-dataset`. Ожидается
   по 39 записей на агента. В `L01`–`L03` сравните раннюю реплику с запросом
   запомненного числа и поздние реплики. Группируйте их по фактическому
   `trimmed_before_answer` и проверяйте событие `context-trim` в трейсе.
4. Проверьте инструментальные задачи по трейсу и снимкам `quizzes` в
   `runs.jsonl`. Учитывайте реальные ID, аргументы и итог правки.
   Оценка Qwen по тексту ответа служит предварительной проверкой.
   Для `Tool correctness` отдельно проверьте наличие каждого ожидаемого
   инструмента из метаданных реплики.
5. В Langfuse сравните прогоны по агенту, версии, типу и сложности. Считайте
   задачу успешной, если прошли все её проверяемые реплики. Стоимость и
   задержка задачи — суммы по её репликам. Считайте долю ошибок и превышений
   лимита по задачам. Для локальной Ollama стоимость определяется ценами
   в конфиге, по умолчанию они равны нулю.

Настройка Qwen в интерфейсе покрывает оценку текста. После завершения оценки запустите
`evaluate.py` для выбранного прогона. Он читает оценки Qwen через API,
проверяет обязательные вызовы, считает Recall@k, Precision@k и MRR,
публикует контекстные оценки и агрегаты `run-summary`. Точные изменения
состояния и причины провалов проверьте при разборе трейсов.
